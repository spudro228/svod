# Планы

Что рассматриваем дальше и с какой оценкой. Не список желаний, а разбор:
по каждому пункту сказано, чего он реально даёт и чем за это платим.

Порядок — по отношению пользы к работе.

## 1. Адреса страниц: перезагрузка возвращает туда же

**Оценка: маленькая работа, ежедневная польза. Делать первым.**

Сейчас маршрутизации нет вовсе: путь к открытой заметке живёт в состоянии
React, адресная строка не меняется. Отсюда три неудобства сразу —
перезагрузка выкидывает в пустой экран, кнопка «назад» уводит из приложения,
а ссылку на заметку нельзя ни отправить себе, ни положить в закладки.

Форма адреса: `/n/<путь к заметке>`. Префикс `n` нужен, чтобы пути с точками
не путались с запросами к файлам сборки. Серверу правок не потребуется —
он уже отдаёт `index.html` на неизвестные пути.

Позиция внутри заметки — отдельный вопрос, и пиксельное смещение тут плохой
ответ: заметку могли поправить с другой машины, и текст уехал. Надёжнее
якорь на ближайший заголовок, `#идентификатор`; идентификаторы у заголовков
уже проставляются при отрисовке. Точное смещение внутри раздела кладём
в `sessionStorage` по ключу «путь + якорь» — это ровно тот случай, для
которого он и придуман: удобство одного зрителя в одной вкладке.

Библиотека роутинга не нужна: у приложения два состояния, список и заметка.
`history.pushState` и слушатель `popstate` — это строк сорок, а `react-router`
принёс бы пятнадцать килобайт и свою модель мышления.

Оценка объёма: около 60 строк.

## 2. MCP-сервер: Claude Desktop и Gemini пишут прямо в свод

**Оценка: самое ценное по существу.**

Свод уже отдаёт HTTP API с токеном, поэтому MCP-сервер — тонкая обёртка,
а не новая подсистема. Отдельный бинарник `cmd/svod-mcp`, общается по stdio,
переиспользует `internal/proto`.

Набор инструментов напрашивается сам:

| Инструмент | Что делает |
|---|---|
| `search_notes` | полнотекстовый поиск, уже есть на FTS5 |
| `read_note` | содержимое плюс бэклинки и теги |
| `create_note` | новая заметка по пути |
| `append_note` | дописать в конец, через `If-Match` |
| `list_recent` | что менялось последним, по логу `seq` |

Приятное следствие устройства: заметка, созданная из Claude Desktop, попадает
на сервер, оттуда её забирает демон и через секунду она лежит на диске
в Obsidian. Никакой отдельной интеграции с Obsidian не нужно — она уже есть.

Claude Desktop понимает MCP из коробки: в конфиг прописывается путь
к бинарнику и переменные `SVOD_SERVER` и `SVOD_TOKEN`.

С Gemini сложнее: своего MCP у него нет, там собственный механизм расширений.
Проще ходить в HTTP API напрямую — он и так есть, отдельной работы не требует.

Оценка объёма: 200–300 строк.

## 3. Временные ссылки: показать заметку без токена

**Оценка: полезно, но это первая фича, выносящая свод в открытый интернет.
Здесь детали важнее самой идеи.**

Замысел простой: нажал «поделиться» — получил ссылку, отправил другу,
через сутки она перестала работать.

Устройство: таблица `shares` с колонками «случайный ключ, путь, когда выдана,
когда истекает, отозвана ли». Ручка `POST /api/v1/share` выдаёт ссылку вида
`/s/<ключ>`, `DELETE` отзывает, список выданных виден в интерфейсе.

Дальше начинается то, ради чего этот раздел написан подробно. Ошибка здесь
означает утечку заметок, поэтому правила такие:

**Ключ случайный, а не производный от пути.** Тридцать два байта из системного
источника случайности. Из хеша пути ключ делать нельзя: угадав схему, любой
подберёт ссылку на соседнюю заметку.

**Одна ссылка открывает ровно один путь.** Ни списка, ни поиска, ни истории,
ни соседних заметок. Отдельная ручка `GET /api/v1/shared/<ключ>`, которая
физически умеет отдать только ту заметку, что записана в строке таблицы.

**Вложения — самая тонкая часть.** Если в заметке есть картинка, она лежит
по своему пути и требует токена; по общей ссылке изображения окажутся битыми.
Значит, при выдаче ссылки надо разобрать заметку, вытащить встроенные
вложения и разрешить доступ именно к этим блобам — и ни к каким другим.
Ровно здесь проще всего случайно открыть доступ ко всему хранилищу блобов.

**Срок живёт на сервере.** Не в ссылке и не в куке. По умолчанию сутки,
на выбор неделя. Истекшая ссылка отвечает так же, как несуществующая, —
чтобы по разнице ответов нельзя было выяснять, какие ключи существовали.

**Заголовок `X-Robots-Tag: noindex`**, иначе заметка окажется в поисковой
выдаче ровно тогда, когда этого меньше всего хочется.

**Страница для гостя отдельная.** Не приложение с флагом «только чтение»:
слишком легко оставить в сборке вызов, который спросит дерево свода целиком.
Отдельный минимальный отрисовщик, знающий одну ручку.

К этому пункту нужны тесты не «работает ли», а «не даёт ли лишнего»:
ссылка на заметку А не открывает заметку Б, истекшая не открывает ничего,
отозванная перестаёт работать сразу.

Оценка объёма: около 250 строк на сервере плюс небольшое окно в интерфейсе.

## 4. Git как способ синхронизации

**Оценка: как транспорт — нет. Как слой истории на сервере — да.**

### Почему не транспорт

Это противоречит решению № 1 из спецификации. Смысл Свода в том, что
синхронизация происходит сама, без явных действий; git же требует
осознанного коммита — то есть возвращает ровно ту работу, от которой уходили.

Три технические причины, каждой хватило бы отдельно:

**Маркеры конфликта пишутся внутрь файла.** При расхождении git оставляет
в заметке `<<<<<<<`, `=======` и `>>>>>>>`. Obsidian покажет это как текст
заметки. Полуслитая заметка хуже двух целых копий рядом — а именно две целых
копии Свод и делает сейчас.

**Вложения раздувают репозиторий навсегда.** Картинка, добавленная и удалённая,
остаётся в истории git насовсем. У нас блобы адресуются по хешу, и одинаковое
содержимое хранится один раз.

**Из браузера так не поработать.** Веб-клиент правит заметки прямо сейчас;
поверх git это означало бы коммит с сервера от лица пользователя — то есть
всё равно свой протокол, только сложнее.

### Где git к месту

Сервер мог бы держать материализованное дерево свода как git-репозиторий
и коммитить каждое принятое изменение с устройством и временем в сообщении.
Тогда появляются `git log`, `git diff`, `git blame` и возможность склонировать
всю историю целиком.

Важно понимать, что это даёт: **не новые данные, а привычные инструменты.**
Полная история у нас уже есть — блобы по `sha256` плюс таблица `versions`.
Git добавил бы к ней знакомый интерфейс, ничего не меняя в протоколе.

Стоимость: рабочее дерево на сервере плюс коммит на каждое изменение.
Для личного свода это копейки. Порядок работы — около 150 строк в `store`.

## 5. Мелочи, каждая на вечер

- **Экран входа не покрыт e2e.** Тесты гоняются против сервера без токена,
  так что форма входа проверена только Go-тестами и руками. Нужен отдельный
  прогон Playwright с поднятым токеном.
- **Мобильная вёрстка.** Три колонки на телефоне не живут. Свод открывается
  с телефона уже сейчас, но пользоваться неудобно. Станет заметно нужнее
  вместе с временными ссылками: их открывают в основном с телефона.
- **Переименование с сохранением истории.** Сейчас это удаление плюс
  создание: содержимое цело, история по новому пути начинается заново.
  Чинится сопоставлением по хешу в пределах одного `seq`.
- **Граф связей.** Данные для него собираются с этапа 3, не хватает только
  отрисовки.
