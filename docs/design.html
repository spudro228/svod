Свод

Личная замена Obsidian: markdown-файлы остаются на диске и правятся чем угодно, демон синхронизирует их с твоим сервером, браузер открывает тот же свод с любого устройства. Гит больше не нужен — версии хранит сервер.

Зафиксированные решения

Девять развилок закрыты. У каждой указано, чем мы за неё платим — чтобы через месяц не пересматривать выбор, забыв, что цена была известна заранее.

№РазвилкаРешениеЧем платим
1Источник правдыЛокальные .md на диске. Сервер вторичен.Сервер не «чинит» испорченный файл — он честно повторит порчу.
2НаправлениеДвустороннее. Браузер тоже пишет.Три пишущих стороны вместо одной → нужен настоящий протокол с версиями.
3УстройстваДве-три машины с демоном + браузер откуда угодно.—
4КонфликтыПобеждает последний, проигравший сохраняется рядом отдельным файлом.Пару раз в год сводить руками. Взамен — ничего никогда не теряется.
5ИсторияПолная. Каждая версия адресуется по sha256.Диск на сервере. Весь твой свод — единицы мегабайт, текст жмётся.
6ХостингVPS в интернете, HTTPS + токен на устройство.Заметки лежат на сервере открыто. Взамен сервер умеет искать и строить граф.
7РедакторПо умолчанию чтение, правка по ⌘E.Нет обсидиановского live preview — разметка не растворяется по мере набора.
8Внешний видПлотный dev-tool в три колонки, тёмная тема по умолчанию, традиционная японская палитра.Не «уютный блокнот». Оптимизировано под навигацию по большому своду.
9Объём v1Синхронизация + wiki-links и бэклинки + поиск + теги.Картинки, граф и мобильная вёрстка — после того, как ядро заработает.
Решение № 4 принято за тебя

Настоящее слияние текста (CRDT, как в Google Docs) — это месяцы работы ради ситуации «я правил один и тот же абзац на двух машинах одновременно». Для личного свода это не окупается.

Вместо этого: побеждает та версия, что пришла последней, а проигравшая ложится рядом файлом … (конфликт, пк, 2026-09-02 14:05).md. Так делает Syncthing, и за годы это ни разу не привело к потере данных — только к паре минут ручного сведения.

Из чего состоит

Три части, но собираются в два исполняемых файла: веб-клиент вшивается прямо в бинарник сервера через go:embed, поэтому деплой — это скопировать один файл и перезапустить сервис.

КомпонентЧто делаетЧто хранит рядом с собой
svod Демон и CLI на машине. Следит за папкой свода, считает хеши, гоняет изменения в обе стороны. .svod/state.db
путь → хеш, last_seq
svodd Сервер на VPS. Присваивает порядок изменениям, хранит содержимое и историю, строит индекс, отдаёт API и веб-клиент. meta.db · blobs/
SQLite + файлы по хешу
веб-клиент SPA: дерево, чтение, правка по ⌘E, поиск, бэклинки. —
ничего, всё с сервера
3

Протокол синхронизации

Это ядро проекта. Веб-морду можно переписать за выходные, протокол — нет, поэтому он описан здесь до строчки.

Четыре правила модели

  1. Единица синхронизации — файл целиком. Не строки, не блоки, не абзацы. Изменил один символ — уехал весь файл. Заметки маленькие, это дешевле любой дельта-логики.
  2. Содержимое адресуется по sha256. Одинаковый текст — один блоб. Переименование файла не перезаливает содержимое, а история версий получается бесплатно как побочный эффект.
  3. У сервера один монотонный счётчик seq. Каждое принятое изменение получает следующий номер. Это и есть глобальный порядок событий — единственный в системе.
  4. Клиент помнит только две вещи: до какого seq он дочитал и карту «путь → хеш» на момент последней синхронизации. Всё в .svod/state.db.

4

Что легко забыть

Шесть мест, где такие проекты обычно ломаются. Каждое стоит пары часов отладки, если вспомнить о нём после, а не до.

ЛовушкаПравило
ЭхоПеред записью пришедшего файла демон кладёт ожидаемый хеш в state. Событие fsnotify с этим хешем игнорируется — иначе изменение уедет обратно на сервер по кругу.
Рваная записьВсегда во временный файл и rename в пределах той же файловой системы. Иначе Obsidian или редактор прочитает половину файла.
Дребезг редактораДебаунс 500 мс тишины по конкретному пути. Редакторы пишут файл в три-четыре приёма, и без дебаунса на сервер уедут три версии вместо одной.
МусорНе синхронизируем: .svod/, .git/, .DS_Store, .obsidian/workspace.json, *.swp, *~. Список лежит в .svodignore в корне свода.
ПереименованиеВ v1 это удаление плюс создание. Блоб не перезаливается — хеш тот же, — но история по новому пути начинается заново. Принято сознательно.
ОфлайнДемон офлайн — правки копятся локально и сливаются по одной при подключении. Браузер офлайн — просто не работает: локального кеша в v1 нет.
5

API

Всё под /api/v1. Демон и браузер ходят в одни и те же ручки — разница только в способе аутентификации: у демона долгоживущий токен устройства в заголовке, у браузера сессионная кука после ввода пароля.

МетодПутьЧто делает
POST/authПароль → сессионная кука на 30 дней. Хеш пароля Argon2id в конфиге сервера.
GET/changes?since=NВсё, что произошло после seq N: путь, хеш, удаление, время. Курсор для догоняющей синхронизации.
GET/blob/{sha256}Содержимое по хешу. Неизменяемо, поэтому кешируется навсегда.
PUT/files/{path}Залить версию. Заголовок If-Match: base_hash обязателен. Ответ 200 с новым seq либо 409 с текущим хешем сервера.
DELETE/files/{path}Надгробие в логе, а не удаление. Тоже с If-Match.
GET/treeДерево свода на текущий seq: пути, размеры, время правки.
GET/note/{path}Содержимое плюс разобранное: frontmatter, теги, исходящие ссылки, бэклинки, структура заголовков.
GET/search?q=Полнотекстовый поиск через FTS5, с фрагментами и подсветкой.
GET/history/{path}Все версии пути: seq, хеш, время, устройство.
WS/streamОдно сообщение на каждый новый seq. Не содержимое — только повод сходить за /changes.
Токены устройств

У каждой машины свой токен, выпущенный командой svodd device add «рабочий мак». Потерял ноутбук — отзываешь один токен, остальные продолжают работать. Общий пароль от браузера при этом менять не нужно.

Дизайн-система

Ниже — не настроение, а значения. Пока они не поменяны здесь, они не меняются в коде: это и есть страховка от бесконечных переделок.

Как это выглядит

Цвет — тёмная тема «墨と藍», тушь и индиго

Палитра собрана из традиционных японских цветов. Это не украшение: у неё есть свойство, которое здесь важно — почти все эти краски получены из растений и минералов, поэтому они приглушены и не спорят друг с другом. Чистого синего или чистого красного в наборе нет вообще, и интерфейс от этого перестаёт кричать. Тёмная основа — 藍墨茶, «индиго-тушь-чай»: чёрный с синим подтоном, каким красили ткань, смешивая индиго с сажей.

Про значения

Названия — настоящие, из традиционного канона. Шестнадцатеричные значения подобраны под контраст на экране, а не переписаны из справочника красителей: у растительной краски нет канонического sRGB, а текст должен читаться. Каждый цвет проверен на своём фоне — минимум 4.5:1 для текста.

Пять правил, которые не дают дизайну расползтись

  1. Один акцентный цвет. Всё, что «выбрано», «активно» или «ссылка» — это 浅葱. Второго акцента в интерфейсе нет; 藤 закреплена за тегами и больше нигде не появляется.
  2. Границы вместо теней. Тень имеют только всплывающие слои: ⌘K, меню, диалоги. Панели разделены линиями.
  3. Один радиус. 4 пикселя. Не 6, не 8, не 12 у карточек.
  4. Не карточки. В интерфейсе нет прямоугольников с рамкой, тенью и отступом. Есть панели, разделённые линиями.
  5. Иконки только в дереве. Папка, файл и точка синхронизации. Всё остальное — текст: кнопки подписаны словами.

Стек

Критерий отбора один: меньше движущихся частей. Ни одной зависимости, которую нельзя объяснить одной строкой.

СлойВыборПочему именно так
СерверGo 1.23 + chi v5Группы маршрутов, аккуратный стек middleware и готовый chi/middleware — логи, recovery, таймауты, request-id из коробки.

Почему chi, а не Gin, Echo или Fiber

Не из аскезы, а из-за одного технического свойства: у chi хендлер остаётся обычным http.Handler, а параметры пути достаются из запроса. Gin и Echo вводят собственный тип контекста, и всё, что написано под стандартную библиотеку, начинает ходить через переходники — включая WebSocket и любой сторонний middleware. Fiber построен на fasthttp и с net/http несовместим вовсе, так что coder/websocket с ним просто не соберётся.

chi даёт ровно то, ради чего берут фреймворк — группы маршрутов, монтирование поддеревьев, цепочку middleware, — и ничего не ломает взамен. Если завтра он разонравится, снять его можно за вечер.

Каркас

Раскладка репозитория, конфиги, схема SQLite, svod init, svodd поднимается и отвечает на /healthz. Ничего ещё не синхронизируется.

Готово, когда: svod status печатает «свод ~/obsidian/Vk, 225 файлов, сервер недоступен».

Э1

Дорога наверх

Первичный скан, fsnotify, дебаунс, .svodignore, блоб-стор, лог seq, PUT /files. Браузер отдаёт сырой текст без всякого оформления.

Готово, когда: правишь файл на маке — через секунду видишь новый текст в браузере на телефоне.

Э2

Дорога обратно

Самый сложный этап. GET /changes, WebSocket, атомарная запись, гашение эха, конфликтные копии, история версий.

Готово, когда: два демона на одной машине в разных папках сходятся к одному состоянию, а одновременная правка в обеих даёт конфликтную копию, а не потерю текста.

Э3

Индекс и поиск

goldmark разбирает [[wiki-links]], #теги и frontmatter. Бэклинки, FTS5, ⌘K, ⌘⇧F.

Готово, когда: ссылка [[📖 Go/00_Main_Index]] кликается, а панель бэклинков сходится с тем, что реально написано в своде.

Э4

Интерфейс и правка из браузера

Дизайн-система из раздела 6 целиком: три колонки, обе темы, все токены. CodeMirror по ⌘E, запись через If-Match, обработка 409 во вкладке.

Готово, когда: пишешь заметку с телефона в метро, и она лежит на маке к моменту, когда ты открыл ноутбук.

Э5

Картинки и вложения

Бинарные блобы, отображение в тексте, вставка из буфера с автосохранением в папку вложений.

Готово, когда: Pasted image 20260421121101.png из твоего свода открывается в браузере.
